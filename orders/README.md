# Orders Module

## Overview

The Orders module is the core trading component of the HedgeIoT platform, managing buy and sell orders for energy flexibility services. It handles order creation, modification, lifecycle management, and clearing processes within Market Time Units (MTUs).

## Purpose

- Manage energy trading orders with price-quantity pairs
- Support buy and sell order types for flexible energy assets
- Handle order lifecycle from creation to clearing
- Integrate with portfolios, nodes, and companies for trading
- Process order clearing and settlement results
- Support market-making and aggregation services

## Key Components

### Controller: `OrdersController`

Handles HTTP requests for order management operations.

#### Endpoints:

- `GET /order/list` - Get orders with filtering by MTU and company
- `POST /order` - Create new trading order
- `PATCH /order/:id` - Update existing order
- `DELETE /order/:id` - Delete order (soft delete)
- `POST /order/mtu/:id/seed` - Seed MTU with test orders

### Service: `OrdersService`

Contains business logic for order management and validation.

#### Key Methods:

- `listOrders(mtuIds?, companyId?)` - Retrieve filtered orders
- `createOrder(data)` - Create new order with validation
- `patchOrder(id, data)` - Update order details
- `deleteOrder(id)` - Soft delete order
- `seedMtuWithOrders(mtuId)` - Generate test data for development
- `validateOrderTiming(mtu)` - Check if trading window is open
- `processOrderClearing()` - Handle order matching and clearing

### Entity: `Order`

Represents a trading order in the system.

#### Key Fields:

- `ord_id` - Primary key
- `ord_name` - Optional order identifier
- `ord_direction` - Order type (BUY/SELL)
- `ord_status` - Current status (ACTIVE, TRANSIT, CLEARED, DELETED)
- `ord_product_type` - Product type (ACTIVE POWER)
- `ord_price_quantity_pairs` - Array of price-quantity combinations
- `ord_clearing_price` - Price at which order was cleared (nullable)
- `ord_clearing_quantity` - Quantity cleared in market
- `ord_clearing_welfare` - Economic welfare generated by clearing

#### Relationships:

- Many-to-One with `MTUEntity` (trading time period)
- Many-to-One with `Company` (order owner)
- Many-to-One with `Portfolio` (asset portfolio, optional for DSO orders)
- Many-to-One with `Node` (trading location)

#### Order Directions:

- **BUY**: Demand for energy/flexibility (consumption increase, generation decrease)
- **SELL**: Supply of energy/flexibility (consumption decrease, generation increase)

#### Order Statuses:

- **ACTIVE**: Order submitted and active in market
- **TRANSIT**: Order being processed by clearing mechanism
- **CLEARED**: Order successfully matched and cleared
- **DELETED**: Order cancelled or removed (soft delete)

#### Product Types:

- **ACTIVE POWER**: Primary product for energy trading

## Business Logic

### Order Creation Workflow

1. **Validation**: Check trading window is open for target MTU
2. **Company Verification**: Validate company ownership and status
3. **Portfolio Linking**: Associate order with portfolio (if applicable)
4. **Node Assignment**: Determine trading node from portfolio or explicit assignment
5. **Price-Quantity Validation**: Validate price and quantity pairs
6. **Order Submission**: Store order with ACTIVE status

### Price-Quantity Pairs Structure

Orders support multiple price-quantity combinations for complex bidding strategies:

```typescript
ord_price_quantity_pairs: [
  { price: 50.0, quantity: 100 }, // 100 MW at €50/MWh
  { price: 55.0, quantity: 200 }, // 200 MW at €55/MWh
  { price: 60.0, quantity: 150 }, // 150 MW at €60/MWh
];
```

### Trading Window Constraints

- Orders can only be submitted during open trading windows
- Trading window closure triggers order aggregation process
- Late orders are rejected with appropriate error messages

### Market Clearing Integration

1. **Order Collection**: Gather all orders for MTU after trading window closes
2. **Aggregation**: Create aggregated curves per node and direction
3. **Optimization**: Use LP solver to find optimal clearing solution
4. **Settlement**: Update orders with clearing prices and quantities
5. **Welfare Calculation**: Compute economic welfare for each participant

## DTOs (Data Transfer Objects)

### `CreateOrderDto`

Order creation data validation.

```typescript
{
  ord_name?: string;                           // Optional order name
  ord_direction: string;                       // BUY or SELL
  ord_product_type: string;                    // Product type
  ord_price_quantity_pairs: PriceQuantityPair[]; // Price-quantity combinations
  ord_fk_mtu_id: number;                      // Target MTU ID
  ord_fk_cmp_id: number;                      // Company ID
  ord_fk_prtf_id?: number;                    // Portfolio ID (optional for DSO)
  ord_fk_nd_id?: number;                      // Node ID (derived if not provided)
}
```

### `PriceQuantityPair`

Individual price-quantity combination.

```typescript
{
  price: number; // Price in €/MWh
  quantity: number; // Quantity in MW
}
```

### `UpdateOrderDto`

Partial update DTO for order modifications.

- Extends `CreateOrderDto` with all fields optional
- Allows order modification before trading window closes

## Database Schema

### Order Table

```sql
CREATE TABLE "order" (
  ord_id SERIAL PRIMARY KEY,
  ord_name VARCHAR,
  ord_direction VARCHAR DEFAULT 'BUY',
  ord_status VARCHAR DEFAULT 'ACTIVE',
  ord_product_type VARCHAR DEFAULT 'ACTIVE POWER',
  ord_price_quantity_pairs JSON,
  ord_clearing_price DECIMAL(10,2),
  ord_clearing_quantity DECIMAL(10,2) DEFAULT 0,
  ord_clearing_welfare DECIMAL(10,2) DEFAULT 0,
  ord_fk_mtu_id INTEGER REFERENCES mtu_entity(mtu_id),
  ord_fk_cmp_id INTEGER REFERENCES company(cmp_id),
  ord_fk_prtf_id INTEGER REFERENCES portfolio(prtf_id),
  ord_fk_nd_id INTEGER REFERENCES node(nd_id),
  ord_date_created TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  ord_date_updated TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  ord_date_deleted TIMESTAMP
);
```

## Business Rules

### Order Submission Rules

- Orders must target future MTUs with open trading windows
- Company must be in ACTIVE status
- Portfolio must belong to the submitting company
- Price-quantity pairs must have positive values
- At least one price-quantity pair is required

### Order Modification Rules

- Orders can be modified only during open trading windows
- Clearing data cannot be modified once set
- Status transitions follow defined workflow

### Order Deletion Rules

- Soft delete preserves audit trail
- Hard delete only allowed for test data
- Cleared orders cannot be deleted

## Market Integration

### Aggregated Curves Creation

Orders are aggregated into buy/sell curves for market clearing:

- Buy orders sorted by price (descending)
- Sell orders sorted by price (ascending)
- Cumulative quantities calculated for each price level

### LP Solver Integration

- Orders feed into linear programming optimization
- Clearing prices determined by market equilibrium
- Quantities allocated based on optimization results

### Settlement Process

- Cleared orders generate settlement results
- Payment calculations based on clearing prices
- Welfare distribution among market participants

## Usage Examples

```typescript
const order = await ordersService.createOrder({
  ord_direction: 'BUY',
  ord_product_type: 'ACTIVE POWER',
  ord_price_quantity_pairs: [{ price: 50, quantity: 100 }],
  ord_fk_mtu_id: 123,
  ord_fk_cmp_id: 456,
  ord_fk_prtf_id: 789,
});
```

### Complex Bidding Strategy

```typescript
const complexOrder = await ordersService.createOrder({
  ord_direction: 'SELL',
  ord_product_type: 'ACTIVE POWER',
  ord_price_quantity_pairs: [
    { price: 40, quantity: 50 }, // Minimum price
    { price: 45, quantity: 100 }, // Preferred price
    { price: 50, quantity: 150 }, // Maximum quantity
  ],
  ord_fk_mtu_id: 123,
  ord_fk_cmp_id: 456,
  ord_fk_prtf_id: 789,
});
```

### Order Filtering and Analysis

```typescript
// Get all orders for specific MTUs
const orders = await ordersService.listOrders([123, 124, 125]);

// Company-specific orders
const companyOrders = await ordersService.listOrders(null, 456);

// Analyze order clearing results
const clearedOrders = orders.filter((o) => o.ord_status === 'CLEARED');
const totalWelfare = clearedOrders.reduce(
  (sum, o) => sum + o.ord_clearing_welfare,
  0,
);
```
